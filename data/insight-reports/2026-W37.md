## 异常与应对
### dominant-owner low
- **可能原因（假设）**：uckkk 账号使用模板批量生成插件，目标是占位或测试而非提供差异化功能。
- **影响面**：该账号 **1285 个插件占全生态 13%**，均分 75，拉高规模数字并稀释真实创新密度，干扰增长率计算与质量基线。
- **应对建议**：DSH 官方应对批量生成账号设置合理限制（如每账号插件数上限、去重检测），并在统计口径中单独标注此类批量贡献；生态用户在评估时关注作者多样性与插件质量而非总数。

### npm-stale low
- **可能原因（假设）**：npm 发布流程未自动化或未纳入 CI，导致仓库更新后未及时发版；也可能存在抢注或版本号错配。
- **影响面**：10 个插件安装侧拿到旧版，用户可能遇到与最新仓库不一致的 API 或功能缺失，高 star 插件（如 dsh-cost-meter）也受影响。
- **应对建议**：插件作者应配置 npm publish 与 release 流水线，发布后校验 npm latest 与 repo version 一致；DSH 官方可在质量分中加入 npm 版本一致性检查并提示用户。

### breaking-release high
- **可能原因（假设）**：dsh 处于 alpha/rc 快速迭代期，接口契约尚未冻结，官方为修复核心架构问题主动引入破坏性变更。
- **影响面**：**3 个 breaking 版本**（dsh-v0.1.3-alpha.1, dsh-v0.1.2-rc.1, dsh-v0.1.2-alpha.3）可能导致依赖旧 API 的插件在升级后出现加载失败或运行时错误，尤其影响未严格 pin 版本的插件。
- **应对建议**：插件作者应立即查看官方 changelog/migration 指南，pin 兼容的 dsh 核心版本，并利用 CI 做多版本测试；生态用户升级前确认所用插件已声明兼容；DSH 官方应在 breaking 发布时提供明确的迁移周期与兼容性标记。

## 下一阶段重点与建议
**插件作者**
- 优先修复 `npm.version-drift`、`exports["./client"]` 缺失等高频 drop，提升质量分至 A/S。
- 适配 dsh breaking 变更，在 manifest 中声明 `engines` 或兼容版本，避免用户升级踩坑。
- 保持 npm 发版节奏，仓库更新后 24 小时内发布对应 npm 包。
- 补齐中文文档（生态 zh 覆盖仅 48%），降低非英文用户使用门槛。

**生态用户**
- 选择插件时参考质量分级（S/A 优先），关注 `published` 状态（topByStars 中 5/8 未发布，star 不代表可安装）。
- 升级 dsh 前检查插件兼容性声明，避免因 breaking 变更导致工作流中断。
- 对高 star 但未发布的插件保持谨慎，优先使用 downloadsTop 中 `covered:true` 且 `inAwesome/inImsai` 收录的项目。

**DSH 官方**
- 对批量账号（如 uckkk）建立防刷与去重机制，发布诚信规模报告。
- 强化 npm 版本一致性与发布纪律检查，在插件页显式标注 stale 与 version drift。
- 为 breaking 发布提供自动化迁移检测与通知，降低生态断裂风险。
- 提升 S 级插件比例（当前仅 2.4%），可通过官方激励或模板改进引导腰部插件升级。
